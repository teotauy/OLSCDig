# Self-Hosted Wallet & Check-In Plan

Planning doc for replacing PassKit with an OLSC Brooklyn-owned membership pass, check-in, and season analytics system.

## Goal

Replace the expensive PassKit dependency with a system we own:

- Members live in our database.
- Check-ins live in our database.
- Apple Wallet / Google Wallet passes are generated by us.
- Admins can scan members through a web page.
- Season exports and dashboards come from our own data.

PassKit becomes unnecessary once Wallet generation, pass links, updates, and check-ins are handled here.

## Signup Delivery And Pass Recovery

Owning the pass system gives us a much better member experience than PassKit alone.

### Automatic Pass Delivery

When someone signs up or is imported:

1. Create or update the member in our database.
2. Attach the member to the current season.
3. Generate their credential token.
4. Generate Apple Wallet pass, and later Google Wallet object/link.
5. Send a welcome email with:
   - Apple Wallet link.
   - Google Wallet link when available.
   - Mobile web pass/recovery link.
   - Basic "how to use it at the bar" instructions.

Sources that can trigger this:

- Squarespace webhook.
- CSV import.
- Admin manual add.
- Future member signup form.

The result: no manual line at the bar just because someone joined recently.

### Self-Service Pass Recovery

Add a public page:

- `GET /recover-pass`
- User enters email address.
- App always responds with the same generic message: "If that email is active, we sent your pass link."
- If a current-season member exists, send a fresh pass email.

Security rules:

- Do not reveal whether an email exists.
- Rate limit by IP and email.
- Log recovery attempts.
- Send only to the email on file.
- Optionally rotate/reissue pass token if abuse is suspected.

Recovery email should include:

- Apple Wallet download link.
- Google Wallet link when available.
- Mobile web pass link.
- Support/contact fallback.

Admin backup:

- Admin can resend a pass from the member detail page.
- Admin can rotate a credential token if a pass was shared/leaked.

This is a major reason to own the system: members can recover passes themselves without tying up the entry line.

## Wallet Strategy

### Apple Wallet

Required:

- Active Apple Developer Program when issuing/updating passes.
- Pass Type ID.
- Pass signing certificate.
- Team ID.
- `.pkpass` generation/signing.
- Hosted pass download links.
- Optional Apple Wallet web service for push updates.

MVP:

- Generate a `.pkpass` with member name, season, QR code, and next match.
- Email/download link from our app.
- Reissue pass when needed.

**Gotcha hit and fixed (Aug 10):** if `APPLE_PASS_CERT_P12_BASE64` is set, the
app uses it and silently ignores `certs/passTypeCert.p12` on disk, even
locally. A stale base64 value left over from earlier testing caused hours of
"invalid password" errors that had nothing to do with the actual password —
every fix to the file itself was being ignored. Lesson: if this ever breaks
again after a cert rotation, check for a stale `APPLE_PASS_CERT_P12_BASE64`
env var before re-debugging the password. Separately: `security export -t
identities` from the CLI is a reliable way to pull a cert+key out of Keychain
without the GUI export dialog (which kept silently producing
mismatched/wrong passwords) — but it bundles *every* identity in the
keychain, so the target one must be isolated by `localKeyID` before
repackaging into a clean single-identity `.p12`.

Later:

- Add Apple Wallet web service registration.
- Push updates when the next match changes.

### Google Wallet

Required:

- Google Wallet issuer account.
- Service account.
- Wallet class/object creation.
- Save-to-Google-Wallet link.

MVP can come after Apple Wallet if most members use iPhone.

## QR Credential Design

Each member gets a random, unguessable credential token.

Example QR payload:

```text
https://olsc.example.com/checkin/t/<random-token>
```

Rules:

- Token should not expose email or member ID.
- Token should be long enough to resist guessing.
- Token can be rotated if a pass is leaked.
- Server looks up the token and records the check-in.
- Admin scanner should submit the token to an authenticated endpoint.

### Barcode Format

QR is the recommended default because it can hold a URL/token payload and scans reliably with phone cameras.

Other possible formats:

- Aztec
- PDF417
- Code 128

Apple Wallet supports multiple barcode formats, but QR is the simplest fit for a web-based scanner.

### Rotating Codes

Rotating codes are possible, but not in the same way inside Wallet passes.

Important constraint:

- Apple Wallet and Google Wallet passes cannot run our JavaScript or generate a new barcode every 30 seconds locally.
- A barcode inside a Wallet pass is static until the pass is updated by our server.
- Server-pushing a new barcode every 30-60 seconds to every member is not a good design.

Recommended approach:

- Use a static, unguessable Wallet token for the normal pass.
- Make check-ins idempotent per member/match so screenshots cannot create multiple check-ins.
- Show member name/status on scan so admins can catch obvious misuse.
- Allow token rotation/revocation if a pass is leaked.

Higher-security option:

- Add a mobile web "live credential" page that generates a short-lived QR/barcode from a per-member secret.
- The Wallet pass can link to that page.
- The scanner verifies the time-windowed code.

Tradeoff:

- Static Wallet QR is fastest and most reliable at the bar.
- Rotating web QR is more secure, but members must open a web page instead of only showing Wallet.

## Admin-Gated Scanner

Yes, scanning can be done through a web page with an admin gate.

### Scanner UX

Admin flow:

1. Admin logs in.
2. Admin opens `/scanner`.
3. Browser asks for camera permission.
4. Admin scans the QR code from Apple Wallet, Google Wallet, or mobile web pass.
5. Page shows a big success/failure state:
   - Member name.
   - Match.
   - Already checked in vs newly checked in.
   - Timestamp.
6. Scanner returns immediately to scan mode.

### Door Staff Result States

The scanner should make status obvious at arm's length.

Recommended states:

- **New valid check-in:** green success state, member name, match, timestamp.
- **Already checked in today / this match:** strong warning state, member name, original check-in time, and "Already used for this match."
- **Invalid token:** red error state with "Invalid pass."
- **Expired/old-season pass:** red error state with "Expired pass."
- **Wrong match/manual review:** amber warning state with admin override option.

For "already used" we should not rely on subtle copy. Door staff should see a distinct color, a large label, and the prior scan time.

### Visual Authenticity Cues

We can add animated/liveness styling to web pages we control:

- Green animated success border after a fresh scan.
- Streaming color border on an optional member live-credential page.
- Bouncing footballs or club-themed motion on the live credential page.
- Large changing timestamp or short code on the live credential page.

Important limitation:

- Apple Wallet and Google Wallet passes themselves are static. They cannot show bouncing footballs or animated borders.
- The admin scanner page can animate scan results.
- A mobile web credential page can animate as a stronger anti-screenshot signal.
- The server-side scan result is still authoritative; animation is a helpful visual cue, not security by itself.

### Scanner Endpoints

Suggested routes:

- `GET /scanner`
  - Admin-only page.
  - Uses phone camera through browser APIs.

- `POST /api/checkins/scan`
  - Admin-only endpoint.
  - Body: `{ "token": "...", "match_id": "..." }`
  - Creates or returns a check-in.

- `GET /api/matches/current`
  - Admin-only or public depending on use.
  - Returns current match for scanner default.

### Scanner Security

- Scanner page must require admin login.
- Check-in API must require admin session.
- QR token must be unguessable.
- Check-in should be idempotent per member/match.
- Log every scan attempt.
- Rate limit invalid tokens.
- Show limited member data on scanner result.

### Scanner Implementation Options

Browser camera libraries:

- `html5-qrcode`
- `zxing-js/browser`

Use whichever works best on mobile Safari and Chrome.

Important browser notes:

- Camera access requires HTTPS in production.
- iOS Safari camera behavior should be tested early.
- The scanner page should have a manual token/member search fallback in case camera access fails.

## Check-In Rules

Recommended rule:

- One check-in per `member_id + match_id`.
- If scanned again, show “Already checked in” with original time.
- Allow admin override only from an admin detail page.

Recommended fields:

- `id`
- `member_id`
- `match_id`
- `checked_in_at`
- `scanner_admin_id`
- `source` (`scanner`, `manual`, `import`)
- `raw_token_hash`
- `notes`

### Future Idea: Match-Day Trivia

Door staff sometimes ask a question of the day at check-in (e.g. "what minute
will the winner be scored in?"). Worth capturing and analyzing later.

Recommended design when this gets built — keep it separate from `checkins`,
not bolted onto it, since a check-in ("did they show up") and a trivia answer
("what did they guess") are different concerns with different lifecycles
(answers get scored after the match; check-ins don't):

- `trivia_questions`: `id`, `match_id`, `question_text`, `correct_answer` (filled in after the match).
- `trivia_answers`: `id`, `member_id`, `match_id`, `question_id`, `answer_value`, `submitted_at`, `is_correct` (set once scored).

This unlocks season-long stuff like "best predictor of the year" without
tangling it into attendance data. Not needed for launch — two-table addition
whenever there's time post-August.

## Match Model

Each check-in should attach to a match record.

Match fields:

- opponent
- home/away
- competition
- kickoff time
- venue/bar location
- final score
- season
- external source ID if imported

Current match selection:

- Default scanner to the next/upcoming match.
- After kickoff, scanner should use the match happening today.
- Admin can override the current match.

## Decision Recommendation

Build this.

Apple Wallet viability is no longer an open question for this season: the hardcoded `.pkpass` signing/install spike succeeded with the active Apple Developer account, Team ID, Pass Type ID, and certificate chain.

The cost savings are worth it if we keep scope tight:

1. DB-owned members/check-ins.
2. Admin web scanner.
3. Apple Wallet MVP.
4. Google Wallet after Apple works.

Do not start by cloning every PassKit feature. Start by owning member identity and check-in history.

## Expected Costs

The cash cost should be much lower than PassKit. The real cost is implementation and maintenance time.

### Required / Likely

| Item | Expected Cost | Notes |
| --- | ---: | --- |
| Apple Developer Program | ~$99/year | Required for Apple Wallet pass certificates and issuing/updating passes. |
| Google Wallet issuer/API | $0 | Google Wallet APIs generally do not add a direct per-pass fee. |
| Hosting | $0-$25/month | Existing Render/Vercel setup may work. Paid hosting avoids sleep/cold starts. |
| Database | $0-$25/month | Supabase/Postgres free tier may be enough; paid tier is better for backups/reliability. |
| Domain | $0-$20/year | Only if we need a new domain/subdomain setup. |
| Email sending | $0-$15/month | Existing SMTP may work; Postmark/SendGrid/etc. if we want reliable delivery. |
| Football-data.org | $0+ | Existing free/API setup may be enough for match lookups. |

### Optional

| Item | Expected Cost | Notes |
| --- | ---: | --- |
| Error monitoring | $0-$25/month | Sentry/etc.; useful but not required at launch. |
| Backups/storage | $0-$10/month | Usually covered by existing cloud storage or DB provider. |
| SMS | Usage-based | Only if we add Twilio/text reminders later. |

### Practical Annual Ranges

- **Bare bones:** about `$99/year` plus existing hosting/tools.
- **Comfortable small production:** about `$200-$500/year`.
- **More polished/reliable:** about `$500-$900/year`.

Even the polished version should be far below PassKit if PassKit remains the largest club software expense.
